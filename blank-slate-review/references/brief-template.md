# 委託書範本

> 何時讀：委託方要派一次冷讀時，複製本檔的〈範本〉段填寫；填不出某一欄就先不要派——那一欄空著，冷讀方會自己補，補的方向不受控。填好的委託書就是冷讀方收到的全部指令，不另寫 prompt。

本檔章節：〈每一欄為什麼存在〉〈範本〉〈一份填好的委託書〉。

## 每一欄為什麼存在

| 欄 | 沒有它會怎樣 |
|----|-------------|
| 盤點對象與對象類型 | 冷讀方不知道要推導什麼形狀的表，只能照自己的習慣列；對象類型決定讀哪一組預設（見 `subject-presets.md`） |
| 為什麼需要冷讀 | 冷讀方不知道委託方的盲區在哪，會把力氣花在委託方已經查過的面向 |
| 冷讀方形態 | 決定「空白」的強度與成本；不寫，派發方會選最便宜的 |
| 輸入白名單與停讀線 | 空白的保證全部來自這一欄。白名單寫錯一個檔，冷讀方讀到被審對象自己的結論，推導就被帶走 |
| 禁讀清單 | 白名單只說能讀什麼，禁讀清單把最容易順手打開的檔案點名——被審對象、依它寫成的補記、同源 reviewer 的報告 |
| 階段 1 表形狀 | 冷讀方自己定義表，階段 2 對照時委託方要先翻譯才能用 |
| 判定與等級定義 | 「必修」在不同對象上指不同的事（資料契約改欄位、API 改回應格式）；不定義，冷讀方的等級與委託方的修法不對口 |
| 產出約束 | 冷讀方與委託方常在同一個 working tree；不寫「只新增一個檔、不改既有檔、不 commit」，冷讀方會順手修 |
| 範圍外處置 | 不寫「照列標範圍外」，冷讀方會直接丟掉，委託方失去「範圍外清單是否完整」這一層檢查 |
| 回報格式 | 委託方要的是路徑、數量、前三項；不寫，冷讀方會把整份報告貼回來 |

## 範本

```markdown
# 冷讀委託：{盤點對象一句話}

## 為什麼要你做
{被審對象與既有審查都出自同一來源的說明；委託方看不到的是「沒寫的東西」}

## 冷讀方形態
{Agent 子代理 ／ 獨立 session}；理由：{對照 SKILL.md 的形態判準}

## 階段 1：獨立推導（先不要讀 {禁讀清單}）
只讀以下：
- {檔案 A}
- {檔案 B}：讀到〈{停讀線標題}〉之前為止。理由：{那一段是依被審對象寫的}
- {檔案 C}：{要讀的章節}；{要跳過的章節}跳過

推出以下表（形狀依 {對象類型} 預設，欄位見 subject-presets）：
1. {表一名稱}：{欄位}
2. {表二名稱}：{欄位}
3. {表三名稱}：{欄位}；起頭情境：{列三到五個}，請自行擴充
寫完先存檔再進階段 2。

## 階段 2：對照
讀 {被審對象清單}，把階段 1 每一項標成：已涵蓋（註明對應位置）／部分涵蓋（缺哪條路徑）／未涵蓋。
未涵蓋與部分涵蓋再分：
- 必修：{對象類型的必修判準}
- 可改：{對象類型的可改判準}
每一項寫明修法落在哪個檔案的哪一節。

## 約束
- 只新增一個檔案：{產出路徑}。內容分「階段 2 對照表」「階段 1 推導」兩節，對照表在前。
- 不修改既有檔案、不 commit。{同一 working tree 的說明}
- 範圍外的項目（{範圍文件}明列不做的）照樣列出，標「範圍外」。
- 推論與文件事實分開標註。
- 階段 1 無法避免看到的被審內容（同一檔內的表、標題），在產出開頭誠實標註看到了什麼、沒讀什麼。

## 完成後
回報：檔案路徑、必修項數量、最重要的三項。
```

## 一份填好的委託書

對象是一個個人 ERP 的第一版用例與資料契約；委託方同一個 session 寫了全部用例與規格，派出的 reviewer 都讀過那些文件。

```markdown
# 冷讀委託：從零盤點 v0.1 的用例，找出用例文件漏掉的場景與跨領域功能

## 為什麼要你做
全部用例與規格都是我這個 session 寫的。我同時在跑多輪審查，但派出的 reviewer 都是同一個來源，看不到「沒寫的東西」。你沒讀過這些文件，你推出來的清單正好拿來對照我漏了什麼。

## 冷讀方形態
獨立 session。理由：委託方與被審對象同作者，且審查結果會改資料表。

## 階段 1：獨立推導（先不要讀用例目錄與規格目錄）
只讀以下三樣：
- 專案說明檔
- 技術決策記錄：讀到〈建立用例後的補記〉之前為止。那段補記是依現有用例寫的，讀了推導會被它帶走。
- 提案：範圍、目標、驗收條件都要讀；frontmatter 的用例清單與缺口表跳過。

推出三張表：
1. 用例清單：行為者／觸發／目標／觸及的領域。
2. 跨領域情境：哪一個領域的動作應該影響另一個、方向、使用者能觀察到什麼。
3. 長時間尺度與生活事件：一週沒開 app、出國換時區、換手機或搬主機、資料匯出、誤刪後回復、地點或藥品改名、合併重複資料、一年後回頭查。這些只是起頭，請自己再擴充。
寫完先存檔再進階段 2。

## 階段 2：對照
讀全部用例與規格，把階段 1 每一項標成已涵蓋／部分涵蓋／未涵蓋。
- 必修：會改到資料表、關聯或事件。
- 可改：只是 UI 或流程層面。
每一項寫明修法該落在哪個檔案的哪一節。

## 約束
- 只新增一個檔案：reviews 目錄下以日期命名的盤點檔。對照表在前。
- 不修改既有文件、不 commit。我同時在改規格，兩邊在同一個 working tree。
- 提案明列不做的項目照樣列出，標「範圍外」。
- 推論與文件事實分開標註。

## 完成後
回報：檔案路徑、必修項數量、最重要的三項。
```

這份委託書執行的結果見 `../examples/usecase-walkthrough.md`。
